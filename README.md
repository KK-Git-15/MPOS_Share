## 1. Project Overview & Architecture Map

### 1.1 What the protocol is

MPOS ("Multi-Path Onion Sharding") is onion routing with three additions on top of plain Tor-style onions:

1. **Reed-Solomon K-of-N erasure coding** (Phase 1). A file is split into `N` shards (default `K=4, N=6`).
   Any `K` shards rebuild it, so up to `N-K` shards can be lost in transit.
2. **Per-shard end-to-end encryption** (Phase 2). Each shard is encrypted with its own AES-256-GCM key
   before it enters the network.
3. **Multi-path onion transport** (Phases 4–5). Every shard travels on a *different*, randomly assigned
   3-hop circuit (Guard → Middle → Exit → Server). Each hop strips exactly one AES-256-GCM onion layer.

No single relay sees every shard, and no relay sees both the sender and the plaintext.
Losing a whole circuit costs one shard, which the K-of-N coding can absorb.

### 1.3 Current wire format (Phases 3–5, `protocol.py`)

```
[4B big-endian metadata_len][metadata_len B UTF-8 JSON][4B big-endian payload_len][payload_len B raw]
```
- One packet per TCP connection; the connection is closed after each packet. There is no ACK.
- `readexactly` is used everywhere. A short read raises `asyncio.IncompleteReadError`.
- No maximum length is enforced. A malicious 4-byte header can make a node allocate up to 4 GiB.

### 1.4 Onion layer format (Phase 5, `onion.py`)

```
layer = [12B random nonce][AES-256-GCM ciphertext || 16B tag]      (associated_data = None)
innermost plaintext = JSON {"metadata": {...shard metadata...}, "payload": base64(Phase-2 ciphertext)}
onion = Guard( Middle( Exit( innermost ) ) )
```
Keys: one random 32-byte key per (circuit, role), stored base64 in `Phase_5/onion_keys.json`.
**They are pre-shared through the local filesystem**, so all relays and the client must run on the same machine.
`get_key()` re-reads the JSON on every call.

### 1.5 End-to-end data flow (as implemented today)

```
SENDER (offline steps)
  Input.txt
   └─ Phase_1 encoder ── RS(K=4,N=6) ──► shards/shard_00..05.bin + metadata.txt (original_size,k,n,padlen)
   └─ Phase_2 encryptor ─ AES-GCM/shard ► encrypted_shards/encrypted_shard_XX.bin + keys/key_XX.bin

SENDER (network, Phase 5 client.py)
  for each encrypted shard i (concurrently):
     circuit c = shuffled assignment (len(shards) MUST == len(circuits))
     onion = Guard_c(Middle_c(Exit_c(JSON{metadata, b64(shard)})))
     TCP ─► Guard 9100+c

RELAYS (relay.py, one process per hop)
  Guard_c  :9100+c  receive → check metadata.circuit_id == own → decrypt guard layer  → TCP ─► Middle :9200+c
  Middle_c :9200+c  receive → check circuit → decrypt middle layer → TCP ─► Exit   :9300+c
  Exit_c   :9300+c  receive → check circuit → decrypt exit layer   → TCP ─► Server :9001

RECEIVER (server.py)
  receive → unpack_final_payload → write received_shards/encrypted_shard_XX.bin

RECEIVER (offline, NOT WIRED UP YET)
  Phase_2 decryptor (needs keys/ from sender; currently reads encrypted_shards/, not received_shards/)
  Phase_1 decoder   (needs metadata.txt; reads shards/, not decrypted_shards/)
```

### 2.3 Code style

The existing code uses heavily vertical formatting (one argument per line), `# =====` section banners, and `[ROLE]`-prefixed `print` logging. For `mpos/`:

- **Formatting:** `ruff format` (88 cols). Keep the `# ====` section banners between major blocks for continuity. Drop the one-token-per-line style.
- **Type hints are required** on every function signature and dataclass field. Use `from __future__ import annotations`, `bytes` and not `bytearray` in public APIs, `pathlib.Path` for paths, and `typing.Final` for constants.
- **Data shapes:** use `@dataclass(frozen=True, slots=True)` for wire/metadata structures, not raw dicts. Use `enum.IntEnum` for frame types and roles.
- **Naming:** `snake_case` functions, `PascalCase` classes, `UPPER_SNAKE` constants. Async functions use verb names (`send_frame`, not `frame_sender`).
- **Logging:** use `logging.getLogger(__name__)`, not `print`. Format: `%(asctime)s [%(name)s] %(levelname)s %(message)s`. Keep `[Guard-3]`-style node names in `extra`/messages. Every log record is *also* published to the `EventBus` so the GUI can show it.
- **Paths:** never use an absolute path literal. Resolve from `Path(__file__).resolve().parents[n]` or config.
- **Docstrings:** one-line summary plus wire format where bytes are involved (the existing code does this well; keep it).

### 2.4 Error-handling protocol

- Hierarchy lives in `mpos/errors.py`: `MPOSError` → `FramingError`, `DecryptError` (wraps `cryptography.exceptions.InvalidTag`) → `LayerDecryptError`, `HopUnreachable`, `TransferTimeout`, `ReassemblyError`, `IntegrityError`.
- **Relay rule:** a relay never crashes on bad input. It logs, emits a `HopFailed` event, closes that stream and keeps serving. A peer that sends malformed frames repeatedly is disconnected.
- **Crypto rule:** any `InvalidTag` means *drop the packet*. Never forward, retry-decrypt, or log plaintext fragments. Log only circuit_id/stream_id and sizes.
- **Network rule:** every `await` on the network has a timeout (`asyncio.timeout(...)`). Connect: 5 s, frame read: 30 s, per-shard end-to-end ACK: configurable (default 20 s).
- Catch broad `Exception` only at task boundaries (connection handler, top-level task). Re-raise `asyncio.CancelledError` every time; never swallow it.
- Always `writer.close(); await writer.wait_closed()` in `finally`, wrapped in `contextlib.suppress(Exception)`, as Phase 5 already does.
- Validate before allocating: enforce `MAX_FRAME = 16 MiB` before `readexactly`.

### 2.5 Security rules (non-negotiable)

- Never reuse a (key, nonce) pair. Use random 12-byte nonces from `secrets`/`os.urandom`, or derive deterministic nonces only from unique counters per key.
- Always bind context with GCM AAD (`circuit_id`, `hop_index`, protocol version) in new code.
- Secrets (`*.pem` private keys, `onion_keys.json`, `keys/`) are git-ignored and written with mode `0o600`.
- Never log keys, nonces with plaintext, or decrypted payloads.
- Use `hmac.compare_digest` for any manual tag/hash comparison.

## 3. Phase-by-Phase Roadmap & Implementation Specs

### Phase 6 — Real Cross-Device Transfer

**Goal:** a file on device A reaches device B through relays running on devices C/D/E (or any mix, including several nodes on one host), without pre-shared key files and with verified, complete reassembly.

#### 3.1.1 Node model & directory
- Replace "3·N relay processes" with **one `NodeDaemon` per device**: `python -m mpos node --config node.toml`. A node can be guard, middle, exit, and receiver for any number of circuits at the same time. Per-circuit state lives in a dict keyed by `(link, circuit_id)`.
- Each node has a long-term **X25519 identity key** (`data/<node_id>/identity.pem`, generated on first run).
- **Static directory** `nodes.json` (copied to every device):
  ```json
  {"version": 1, "nodes": [
    {"id": "alpha", "host": "192.168.1.20", "port": 9100, "pubkey": "<b64 X25519>", "roles": ["relay","receiver"]}
  ]}
  ```
  `python -m mpos keygen --id alpha --host ... --port ...` prints the entry to paste in.
- Listeners bind `0.0.0.0` (configurable). Hosts are resolved from the directory, never hardcoded.

#### 3.1.2 Frame format v2 (`net/framing.py`)
```
| magic "MP" 2B | ver 1B | type 1B | flags 1B | circuit_id 4B | stream_id 4B | length 4B | body length B |
```
- Types: `HELLO`, `HELLO_ACK`, `ONION`, `DATA_ACK`, `PING`, `PONG`, `CLOSE`, `ERROR`.
- `length <= MAX_FRAME (16 MiB)`; otherwise raise `FramingError` and drop the link.
- **Multiplexing:** one persistent TCP link per peer pair (`net/link.py`), many circuits/streams per link. A per-link writer lock (`asyncio.Lock`) serializes frames. Each `(circuit_id, stream_id)` gets an `asyncio.Queue`. Use a bounded send queue for backpressure.
- `HELLO` exchanges node_id and protocol version. Reject mismatched versions with `ERROR`.

**As implemented in 6d** (`net/link.py`, `net/node.py`, `net/directory.py`):
- Each ONION frame carries one whole onion. Multiplexing means many onions share one persistent link, each with a per-link `circuit_id`; there are no per-stream queues yet (add them only if 6e needs them).
- HELLO is **not authenticated**. So a node only *sends* over links it dialed itself, to the directory address, and checks that the peer names itself as the expected node. Inbound links are receive-only, apart from PONG replies.
- Peer misbehaviour (bad handshake, malformed or oversized frame, bad layer, unknown or dead next hop) drops the frame or link and increments `NodeDaemon.stats`. Nothing raises out of the daemon.
- Idle reads on an established link have no timeout. A peer that stalls mid-frame holds one task until Phase 8's PING liveness check closes the link.
- `NodeDaemon.delivered` (an `asyncio.Queue[bytes]`) is the hand-off point to `transfer.py` in 6e.

#### 3.1.3 Onion v2 — self-routing, no pre-shared keys (`crypto/onion.py`) ✅ implemented
For each hop the sender generates a fresh ephemeral X25519 key `e` and derives
`k = HKDF-SHA256(ECDH(e, node.pub), salt = e.pub || node.pub, info = b"mpos-onion-v2")`.
```
layer   = [1B ver=2][32B e.pub][12B nonce][AESGCM_k(routing_header || inner) || 16B tag]   AAD = ver || e.pub
routing = [1B cmd RELAY=1|DELIVER=2][1B id_len][64B node_id, zero padded]                  (66 B)
DELIVER inner = [4B payload_len][payload][zero pad to a 4 KiB bucket]
LAYER_OVERHEAD = 127 B per hop
```
- API: `build_onion(route: list[Hop], payload) -> bytes`; `peel_layer(onion, identity_key) -> PeeledLayer(command, next_hop, payload)`. Any failure raises `LayerDecryptError` and the caller drops the packet.
- The route is inside the onion (fixes G4), and relays need no `onion_keys.json` (fixes G3). Routes may include the receiver as the final DELIVER hop, so the exit relay never sees the payload.
- Hop index and circuit_id are **not** in the KDF/AAD: a relay cannot know its own position without leaking it. Per-layer uniqueness comes from the fresh ephemeral key. Circuit binding belongs to the link layer (6d).
- Known limitation: only the innermost payload is bucket-padded. Each layer adds a constant 127 B, so a relay can infer how many layers remain. Hiding that needs a Sphinx-style fixed-length header; out of scope, so document it in the report.
- Innermost payload is binary, not base64 JSON (fixes G9). The shard header format is defined in 6e (`transfer.py`).
- Trade-off to document in the report: no forward secrecy against later compromise of a relay's static key, because there is no telescoping circuit handshake. That is acceptable for this project.

#### 3.1.4 End-to-end shard encryption (replaces `keys/` dir)
- Per transfer: the sender does ECDH(ephemeral, receiver.pub) → HKDF → `file_key`. Per-shard keys are `HKDF(file_key, info=transfer_id||segment||shard_id)`. The ephemeral pubkey travels in the manifest, so the receiver can derive every key and nothing secret touches disk.

#### 3.1.5 File chunking & transfer protocol (`net/transfer.py`, `net/messages.py`, `net/paths.py`) ✅ implemented
`TransferService(node, identity, output_dir, config=TransferConfig(...))` is the single consumer of `node.delivered`. `await service.send_file(path, "bob")` returns a `SendResult`; completed incoming files appear on `service.received`.

Messages (the DELIVER payload: `[1B type][4B hdr_len][JSON header][body]`):
| Type | Direction | Contents |
|---|---|---|
| MANIFEST | S→R | transfer_id, sender, filename, size, sha256(file), segment_size, K, N, sender ephemeral pubkey |
| MANIFEST_ACK | R→S | transfer_id + HMAC |
| SHARD | S→R | transfer_id, segment, shard; body = AES-GCM shard (key and AAD bound to the position) |
| SHARD_ACK | R→S | transfer_id, segment, shard + HMAC |
| COMPLETE | R→S | transfer_id, ok, receiver's sha256 + HMAC |

1. **Keys:** `file_key = HKDF(X25519(sender_eph, receiver_identity))`. Per-shard keys and the ACK HMAC key are derived from it, so no key files exist and only the two endpoints can produce valid ACKs.
2. **Order:** the manifest goes first and is ACKed before any shard is sent, because shards travel on different paths and can arrive in any order.
3. **Segments** (default 1 MiB) are read lazily, and up to `window` (4) are in flight. Each is RS-encoded into N shards, and each shard is sent on its own 3-relay path, ending at the receiver.
4. **A segment is done when any K shards are ACKed.** Un-ACKed shards are re-sent on new paths with exponential backoff, up to `max_retries`. The rest are cancelled once K arrive.
5. **Path choice** (`choose_path`) ranks relays by (penalty, usage in this segment, random), so shards spread over disjoint relays where possible:
   - **Shared node health:** a per-service penalty table used by both the sending and replying sides. A refused first hop adds +3, and a path that delivers clears the penalty of every node on it.
   - **Per-transfer penalty:** every relay on a timed-out path gets +1.
   - **Nothing is banned outright,** so small networks keep working.
6. **The receiver** decrypts each shard, checks its size, and holds shards in memory until K have arrived. It then decodes, writes at the segment's offset in `.<tid>.part`, and ACKs every valid shard, including duplicates, whose earlier ACK was probably lost. ACKs and replies travel back over **2 different paths** each.
7. **Finish:** the receiver checks the whole file's sha256, then reserves a non-clobbering name (`report (1).txt`) and renames the `.part` file atomically. It then sends COMPLETE. The sender succeeds only on `COMPLETE(ok=true)`; `ok=false` raises `IntegrityError`.
8. **Lost COMPLETE:** the sender re-sends the MANIFEST as a status query, and the receiver answers duplicates with its current status.
9. **Deviations from the original plan:**
   - There are no per-shard hashes in the manifest; the GCM tag plus position-bound AAD covers this.
   - Received shards are kept in memory, not on disk.
   - **Resumability after a restart is deferred to Phase 8.**

#### 3.1.6 Phase 6 acceptance criteria
- [~] Transfer of a 50 MB binary across ≥2 physical devices with ≥3 relay nodes; the `sha256` matches. **Verified across separate OS processes on one machine** (50 MB in 1.1 s, 0 retries, receiver-confirmed sha256). **Physical multi-device run still to do**; follow `Phase_6/README.md` §2.

### Phase 7 — GUI (`mpos/gui/`, PySide6) ✅ implemented (`Phase_7/README.md`)

#### 3.2.1 Threading architecture
```
Qt main thread (GUI)  ◄── Qt Signal(event) ──  Bridge  ◄── asyncio.Queue ──  EventBus  ◄── engine (asyncio loop in a QThread / threading.Thread)
        │                                                                                     ▲
        └────────── commands: asyncio.run_coroutine_threadsafe(engine.cmd(...), loop) ────────┘
```
- The GUI **never** opens sockets or calls crypto directly. It sends commands (`StartNode`, `SendFile`, `InjectFault`, ...) and renders events.
- Events (`mpos/events.py`, frozen dataclasses): `NodeStatus`, `LinkUp/Down`, `CircuitBuilt(path)`, `HopForwarded(circuit, hop)`, `HopFailed(reason)`, `ShardSent/Acked/Retried`, `SegmentDecoded`, `TransferProgress`, `TransferComplete(sha_ok)`, `LogRecord`.
- Throttle UI updates: coalesce progress events to ≤ 20 Hz with a `QTimer`.

#### 3.2.2 Layout (one `QMainWindow`, left nav + stacked panels)
1. **Nodes / Connection:** directory table (id, host:port, roles, status LED, RTT); local node start/stop; load `nodes.json`; generate identity.
2. **Live Routing Map:** `QGraphicsView`. Sender on the left, receiver on the right, relays in the middle. Active circuits are drawn as coloured polylines; hops animate on `HopForwarded`. Red marks a failed hop and dashed marks a rerouted path. Click a circuit to see its path and shard ids.
3. **Send / Receive:** file picker, receiver dropdown, K/N and segment-size spin boxes, Send button. The transfer list has per-file progress and a **segment × shard grid** (cells: pending / in-flight / acked / failed / reconstructed-without). Incoming transfers show the save location and integrity result.
4. **Fault Lab (Phase 8):** controls in §3.3.
5. **Logs:** filterable (level, node, circuit, transfer) `QTableView` backed by a ring buffer of 10k records; export to `.log`.

Wraps `Link.send_frame` and the node accept path. Configured per node, per link, or globally, at runtime from the GUI or `python -m mpos fault ...`:
| Fault | Parameters |
|---|---|
| `drop` | probability p |
| `delay` | mean/jitter ms |
| `corrupt` | probability, flips random bytes **inside the onion body** (must trigger GCM `InvalidTag` at next hop) |
| `duplicate` | probability |
| `truncate` | probability (forces `IncompleteReadError`) |
| `node_kill` / `node_revive` | node id: stop the listener and drop all links |
| `partition` | set of node ids that cannot reach each other |
| `blackhole` | node accepts and silently discards (the hardest case to detect) |
All randomness comes from a seeded `random.Random(seed)` per run, so runs are reproducible.

#### 3.3.2 Fault tolerance mechanisms
1. **Detection:**
   - Hop level: connect failure or `PING` timeout (heartbeat every 2 s, 3 misses mean down) updates directory health.
   - Crypto level: `InvalidTag` → drop + `HopFailed(corrupt)`.
   - End to end: no `DATA_ACK` within the timeout means the shard is presumed lost. This catches blackholes.
2. **Recovery:**
   - A segment is complete when **any K** shards are ACKed. Lost shards are never needed if K arrive.
   - Retransmit by **resending only the missing shard ids** on a **new path** that excludes every node on the failed path (the suspect set). Use exponential backoff (0.5 s · 2ⁿ, max 5 retries).
   - If the healthy nodes are not enough for disjoint paths, relax disjointness and log a warning. If fewer than 3 healthy relays remain, pause the transfer and emit `TransferStalled`.
   - Optional adaptive redundancy: if the observed loss rate exceeds (N−K)/N, raise N for later segments.
3. **Integrity:** GCM tag per layer, then sha256 per shard (manifest), then RS decode, then sha256 of the whole file. A mismatch at the final check raises `IntegrityError`, and the transfer re-requests the segment.
4. **Receiver dedupe:** idempotent writes keyed by `(transfer_id, segment, shard_id)`, so duplicates are harmless.

- Retries per segment distribution.

#### 3.4.1 Phase 9a — Entry guards (`mpos/net/guards.py`)

**Why (theory).** The first relay on a shard's path sees the sender's address. Today every shard draws a fresh random first hop, so a transfer of `S` segments gives an adversary that controls a fraction `f` of the relays about `S·N` independent chances to be the first hop (and to match timing if it also holds the last hop). With 600 paths and `f = 0.1`, the chance that at least one path has an adversary at both ends is about `1 − (1 − f²)^600 ≈ 99.8%`. Guards fix the first-hop set once and reuse it, so exposure becomes a single draw instead of `S·N`. The trade-off is that a bad guard sees the sender on every shard that uses it. So use **3 primary guards** and spread each segment's shards over them: each guard sees about `N/3` shards, which preserves MPOS's "no single relay sees every shard" property. Guards do not hide the sender from the guard itself and do not stop a global observer.

**Design**
1. **Config:** `GuardConfig` (`@dataclass(frozen=True, slots=True)`): `enabled=True`, `primaries=3`, `backups=2`, `lifetime_days=30`, `fail_threshold=3`, `min_usable=2`, `reply_via_guards=True`. Add it to `TransferConfig` as `guards: GuardConfig | None`. `None` means old behaviour, and that is the default until acceptance passes.
2. **`GuardSet` API:** `GuardSet.load_or_create(path, directory, self_id, config, rng, now)`, `usable(exclude: frozenset[str]) -> list[str]`, `mark_failure(node_id)`, `mark_success(node_id)`, `refresh(directory, now)` (rotation), `to_json()` / `from_json()`. Per guard: `{id, added_at, role: "primary"|"backup", fails, down}`. Production `rng` is `secrets.SystemRandom()`. Tests inject a seeded `random.Random`.
3. **Selection:** eligible = directory nodes with `"relay"` in `roles` and `id != self_id`. Sample `primaries + backups` distinct nodes. The first `primaries` become primaries. If fewer relays exist, take what exists and log a warning.
4. **Path choice:** add an optional keyword `guards: GuardSet | None = None` to `choose_path` (default keeps old behaviour). Manifest and status-query paths (2 per attempt in Phase 8) use the same function, so they get guards too.
   - First hop: candidates are `guards.usable(exclude={sender, receiver})`, ranked by the existing key `(penalty, usage in this segment, random)`. This spreads a segment's N shards evenly over the guards.
   - Hops 2 and 3: existing ranking over the remaining relays, with `is_guard` added as a soft tie-break after `penalty`, so non-guards are preferred when at least 2 remain. Never ban a guard from hops 2 and 3: small networks must keep working.
   - `usable()` returns healthy primaries first, then healthy backups until `min_usable` is reached. "Healthy" means not `down` in the `GuardSet` **and** not Down or Suspect according to `mpos/net/health.py`. A recovered primary is preferred again immediately.
   - **Never stall because of guards.** If `usable()` is empty, fall back to the unrestricted first-hop choice, log a warning and emit `GuardFallback`.
5. **Failure tracking:** two signals.
   - Call `mark_failure(first_hop)` where the code already adds the +3 penalty for a refused first hop. `fail_threshold` consecutive failures set `down=True`, and `mark_success` on any delivery through that guard resets it.
   - Read the Phase 8 health status at `usable()` time: `Down` = 3 missed pings, `Suspect` = pings answered but probes lost, i.e. a blackhole. Do not build a second detector.
   - A down or suspect guard stays in the set, so it returns when it recovers.
6. **Rotation:** run `refresh()` at transfer start only, never mid-transfer. Drop guards that were removed from the directory, lost the `relay` role, or are older than `lifetime_days`. Replace primaries from backups first, then from new random picks not already in the set. Persist after any change.
7. **Return path:** when `reply_via_guards` is on, the sender adds `reply_via: [<up to 3 usable guard ids>]` to the MANIFEST header. The receiver validates every id against its own directory (must exist, have the `relay` role, not be itself or the sender) and uses valid ones as the **last relay** of every reply path (ACK, COMPLETE, manifest status replies). Phase 8 sends these over 2 paths, or 4 for repeats, so spread them over the guards. Otherwise it keeps the old behaviour. Document that this tells the receiver the sender's guards. It is an accepted, switchable trade-off.
8. **Persistence and privacy:** `data/<node_id>/guards.json` = `{"version": 1, "guards": [...]}`, written atomically with mode `0o600` (`data/` is already git-ignored). A missing or corrupt file means regenerate, never crash. Never log guard ids on relay nodes, and never send them anywhere except via `reply_via`.
9. **Events and UI:** `GuardSelected(node_id, role)`, `GuardStateChanged(node_id, down)`, `GuardFallback(reason)`. Nodes panel gets a **Guard** column (P/B badge). The routing map outlines guard nodes. The Packet Inspector honesty line gains: *"Guards limit long-term exposure; the guard still learns your address."* Logs show the events.
10. **CLI:** `mpos guards list|reset --id X --directory nodes.json [--data-dir D]`; `mpos send ... [--no-guards] [--guards N]`.
11. **Limits to state in the report:**
    - On a 5-relay network with 3 guards, most of the network is a guard, so the benefit is small. It grows with 10+ relays.
    - The unsigned `nodes.json` means whoever edits it chooses your guards.
    - The guard set is a persistent identifier for any relay that watches you across transfers.

#### 3.4.2 Phase 9b — RTT-based window (`mpos/net/congestion.py`)

**Why (theory).** The window is how many shards may be un-ACKed at once. The ideal is the bandwidth-delay product: enough to keep the pipe full but no standing queue. Too large, and relay queues grow, latency rises, ACKs arrive after the timeout and the sender re-sends shards that were never lost (spurious retransmits), which adds load. Too small, and the sender idles. **Loss is not a usable signal** here: every hop runs over TCP, and a missing ACK can mean congestion, a killed relay or an injected fault. So use **delay**, as Tor 0.4.7 does. TCP Vegas estimates how many of our shards are sitting in queues:

```
queued ≈ cwnd × (1 − base_rtt / rtt_cur)
queued < alpha  → grow cwnd by 1 per round     (pipe not full)
queued > beta   → shrink cwnd by 1 per round   (queues building)
otherwise hold
```
Example (alpha=2, beta=4, base 40 ms, cwnd 24): rtt 41 ms → queued 0.6, grow; 44 ms → 2.2, hold; 60 ms → 8.0, shrink. The window settles where a small steady queue exists.

**Design**
1. **Units:** the window is counted in **shards**. `window_mode="fixed"` keeps the old 4-segment window. Add `TransferConfig.window_mode: Literal["fixed", "rtt"] = "fixed"` (flip to `"rtt"` in the last commit, once acceptance passes) and `TransferConfig.congestion: CongestionConfig` (frozen dataclass).
2. **Dispatcher:** release shards segment-major while `inflight < floor(cwnd)`. Read and RS-encode segments **lazily**, only when the dispatcher needs shards. A hard cap `max_inflight_bytes` (default 64 MiB) limits how many encoded segments are held. A shard leaves `inflight` when it is ACKed, when its segment reaches K ACKs (the rest are cancelled, with no RTT sample), or when it times out. A timed-out shard goes to the **front** of the queue and is re-sent on a new path, as today.
3. **RTT samples:**
   - Take `t_send` from the injected clock immediately before the first-hop link write. Do not include RS encode, encryption or onion build time.
   - Take the sample on the first `SHARD_ACK` for `(segment, shard)`.
   - **Karn's rule:** a shard that was ever retransmitted produces no sample.
   - Ignore samples from shards smaller than 50% of the nominal shard size (the short last segment), because they would drag the baseline down.
4. **`RttEstimator` (RFC 6298):**
   - First sample: `srtt = r`, `rttvar = r/2`.
   - After that: `rttvar = 0.75·rttvar + 0.25·|srtt − r|`, then `srtt = 0.875·srtt + 0.125·r`.
   - `rto = clamp(srtt + 4·rttvar, min_rto=1.0 s, max_rto=ack_timeout)`. The old `ack_timeout` (20 s) becomes `max_rto`. The initial `rto` is 5 s.
   - Each timeout doubles `rto` (up to `max_rto`) until the next valid sample resets it.
   - The per-shard ACK deadline is `rto` instead of the fixed value. The retransmit backoff (0.5 s · 2ⁿ, max retries) is unchanged.
5. **Baseline under path diversity:** shard paths differ (different relays, different delay), so one global minimum would make normal variation look like queueing. Therefore:
   - `base(first_hop)` is the minimum sample over the last `base_window_s=30` s **for that first-hop relay**. With fewer than 3 samples, use the global 10th percentile instead.
   - Each sample's `ratio = rtt / base(first_hop)`.
   - A **round** is about one RTT: it ends when the shard sent right after the round began is ACKed. At round end, `q = cwnd × (1 − 1 / max(1, median(ratios in the round)))`.
   - If Experiment E2 shows this is noisy, fall back to the global 10th percentile. Record the choice in `Phase_9/README.md`.
6. **`VegasController`:** pure and synchronous, with an injected clock and no asyncio, so it can be unit-tested.
   - **Bounds:** `init_cwnd = N`, `min_cwnd = 2`, `max_cwnd = max_window_segments × N` (default 16).
   - **Defaults (tunable):** `alpha=2.0`, `beta=4.0`, `gamma=4.0`.
   - **Slow start:** +1 per valid ACK sample (doubles per RTT). Leave it when `q > gamma` or `cwnd ≥ ssthresh`, then set `ssthresh = cwnd`.
   - **Congestion avoidance:** once per round, apply the grow, shrink or hold rule above.
   - **App-limited:** do not increase unless `inflight ≥ cwnd − 1` at ACK time (so the window does not inflate near the end of a file).
   - **Timeouts:** a timeout on shards sharing one first hop, or on at most one distinct relay, changes **nothing** in `cwnd` (the existing per-path penalty handles it). A **burst** (at least 50% of inflight shards, minimum 3, timed out within one `rto` across at least 2 distinct first hops) sets `cwnd = max(min_cwnd, cwnd/2)`, `ssthresh = cwnd`, switches to congestion avoidance, at most once per `rto`, and backs off `rto`.
   - **Interface:** `on_ack(sample)`, `on_timeout(shards)`, `can_send(inflight) -> bool`, plus read-only `cwnd`, `mode`, `queue_est`.
7. **Receiver ACK timing — check first:** open `transfer.py` and see when `SHARD_ACK` is sent. If it is only sent after K shards are decoded, every "RTT" would measure the slowest of K paths. In that case change the receiver to ACK each valid shard **on arrival** (wire-compatible, since `SHARD_ACK` already exists) and add a test. Keep ACKing duplicates.
8. **Results and stats:** extend `SendResult` with defaulted fields `retries`, `final_cwnd`, `peak_cwnd`, `srtt_ms`. Add `duplicate_shards` to the receiver's stats. A duplicate shard arrival means the original had arrived too, so it is a **spurious retransmit** count that needs no wire change.
9. **Events and UI:** `CwndChanged(transfer_id, cwnd, inflight, srtt_ms, base_rtt_ms, queue_est, rto_ms, mode)`, published at most 4 times a second per transfer. The Send/Receive panel gets a small **custom-painted** line widget (cwnd and srtt over time, no new dependency). The segment × shard grid is unchanged.
10. **CLI:** `mpos send ... --window fixed|rtt [--init-cwnd N] [--max-cwnd-segments M] [--trace-cwnd out.csv]`. The CSV columns are `t_s,cwnd,inflight,srtt_ms,base_rtt_ms,queue_est,rto_ms,mode`.
11. **Pitfalls:**
    - The window must never exceed `max_inflight_bytes`.
    - A fractional `cwnd` is floored when sending.
    - Do not halve on a single timeout (blackholes are handled by path penalties and guards).
    - Do not use wall-clock time anywhere in the controller. Inject the clock.
    - Every attempt must send a **freshly built onion**: the relay `ReplayCache` silently drops a layer whose one-time key it has already authenticated.
    - The receiver journals before each ACK (`mpos/net/journal.py`), so ACK latency includes that write. It is part of the real RTT, so do not subtract it, and do not add extra synchronous disk writes on the ACK path.

The new scenarios are opt-in and not part of `all` until they are stable. Use the real `choose_path` and `TransferService`, not re-implementations.
- **E1 `guard_exposure`:** (no cluster, calls `choose_path` directly) Monte Carlo on a synthetic directory of R ∈ {5, 10, 20} relays, adversary fraction f ∈ {0.1, 0.2, 0.3}, transfers of S segments, guards on and off. Metrics: P(adversary is first hop of ≥1 shard) and P(≥1 shard path has an adversary at both first and last hop).
- **E2 `window_vs_latency`:** `fixed` vs `rtt` × added delay {0, 25, 50, 100, 200} ms × a 50 MB file. Metrics: goodput, completion time, retries, `duplicate_shards`.
- **E3 `slow_relay`:** a mid-transfer slow or blackholed relay, `fixed` vs `rtt`. Metrics: time to recover, `duplicate_shards`.
- **E4:** cwnd and srtt traces from `--trace-cwnd`, for the report figure.

**As implemented** (`mpos/faults/scenarios.py`; results and deviations D22–D25 in `Phase_9/README.md`):
- Scenarios `guard_exposure`, `window_vs_latency`, `slow_relay` and `cwnd_trace` (E4), all opt-in; `ALL_SCENARIOS` keeps `all` to Phase 8.
- E3 uses a 16 MB file (the fixed window has 4 MiB in flight at once) and reports `first_retry_ms`, the time from the fault to the first retransmit.
- `--quick` shrinks every Phase 9 scenario (2 MB files, fewer settings). Trace CSVs go to `<out>/traces/`.
- **Results** (in `Phase_9/README.md`): guards cut first-hop exposure on 20 relays from ~100 % to one draw (29 % at f = 0.1). rtt is +27–55 % goodput at 25–200 ms and equal at 0 ms. It detects a blackhole in 1.0 s vs 10.5 s. Short transfers gain nothing. **Known weakness:** at +200 ms, `rttvar` collapses and a burst of spurious timeouts halves the window. A variance floor on `rto` is not implemented.

### 4.5 Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `ModuleNotFoundError: zfec` | Wrong interpreter; `source .venv/bin/activate`. If zfec fails to build on 3.14, use 3.13 |
| `bad interpreter: /Users/anbu/...` | Stale venv. Recreate it (§4.1) |
| `FileNotFoundError: /Users/anbu/...` | Hardcoded path (G1) |
| `OSError: [Errno 48] Address already in use` | Old relays are still running: `lsof -nP -iTCP:9100-9399 -sTCP:LISTEN` then `kill <pid>`. Phase 5: always stop the launcher with Ctrl+C |
| `Onion key file not found` | Start `launcher.py` before `client.py` (Phase 5) |
| `cryptography.exceptions.InvalidTag` at a relay | Key mismatch: the launcher was restarted after the client built its onion, the wrong circuit/role, or (Phase 6) a stale `nodes.json` pubkey. Also expected under Phase 8 corruption |
| `Number of shards and circuits must be equal` | Phase 5 limitation (G10). The relay count is set at launch from `encrypted_shards/` |
| `Next hop unavailable` / `ConnectionRefusedError` | Downstream node not started. Start order is server → exit → middle → guard (the launcher does this) |
| Cross-device connect times out | Listener bound to `127.0.0.1` (must be `0.0.0.0`), macOS firewall (System Settings → Network → Firewall: allow Python), devices on different subnets, or client-isolation Wi-Fi. Test with `nc -vz <host> <port>` |
| `IncompleteReadError` | Peer closed mid-frame. Expected under `truncate` faults; otherwise check for the sender closing before `drain()` |
| Decoder: `Not enough shards available` | Fewer than K shards arrived. Phase 8 retries should prevent this. Check ACK timeouts |
| Reconstructed file has trailing bytes | Did not truncate to `original_size`/segment `original_len` after RS decode |
| `Exception ignored ... _SelectorTransport.__del__ ... 'NoneType' object is not iterable` at shutdown | CPython asyncio race: a peer connected in the same loop iteration as `server.close()`. Harmless. In tests, stop `TransferService`s and let traffic settle (`asyncio.sleep(0.1)`) before stopping nodes |
| Transfers crawl (minutes instead of seconds) in a GUI test or script | `QTest.qWait` holds the GIL while sleeping, which starves the engine thread (0.7 s → 500 s). Wait with `processEvents()` + `time.sleep()` (`tests/gui/qt_helpers.py`). The real app's `app.exec()` is fine |
| GUI freezes | Blocking call on the Qt thread. All network work must go through `run_coroutine_threadsafe` |
| `GuardFallback` warning / no guards used (Phase 9a) | All guards are Down/Suspect or excluded (for example the receiver is one of your guards on a tiny network). Check `mpos guards list`, node health and `min_usable`. Transfers still work on the fallback path |
| Guards look stale after editing `nodes.json` (Phase 9a) | Guards are persistent by design. Removed nodes are dropped at the next transfer start; use `mpos guards reset` to force a new selection |
| `cwnd` stuck at `min_cwnd` or never grows (Phase 9b) | Usually a bad baseline: path diversity inflating `rtt/base`, a clock that is not monotonic, or samples taken after RS/onion build time. Check `--trace-cwnd`, the per-first-hop baseline and where `t_send` is stamped |
| RTT samples look absurdly large (Phase 9b) | The receiver ACKs only after decoding K shards (measures the slowest path). ACK each valid shard on arrival (§3.4.2 item 7) |
| Retransmitted shards silently vanish (Phase 9b) | A retransmit re-sent the *same onion bytes*, and the relay `ReplayCache` dropped it. Always rebuild the onion (fresh ephemeral keys) for every attempt |
| Integration timing test is flaky (Phase 9) | Absolute timings on a shared machine. Compare `rtt` against `fixed` in the same run and widen margins; never assert exact milliseconds |
